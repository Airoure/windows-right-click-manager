# 初步架构方案

## 范围和顺序

清理、恢复和自定义菜单均纳入项目范围，优先完成清理与恢复。

第一版针对 Windows 10 的传统右键菜单；Windows 11 新版菜单的管理能力后续单独评估。

实施顺序：

1. 建立 Tauri 2、React、TypeScript 和 Rust 项目骨架。
2. 只读扫描传统菜单注册信息，区分静态命令与动态 Shell 扩展。
3. 实现已验证类型的禁用、恢复及操作历史。
4. 添加自定义程序和脚本菜单。
5. 逐类扩展动态菜单支持，并评估 Windows 11 新版菜单。

## 模块职责

- React 界面：显示扫描结果和操作能力，收集用户意图。
- 扫描器：读取菜单注册信息，保留实际来源、注册表视图及作用位置。
- 规则层：根据菜单类型判断操作方式、影响范围和权限要求。
- 执行器：校验变更计划，保存原始状态，执行操作并重新读取验证。
- 恢复记录：持久保存操作前后状态和执行结果，支持撤销及冲突检测。
- 管理员辅助进程：仅处理需要提升权限的受限系统操作。

模块先按职责组织在一个应用中，避免过早拆分服务或引入数据库。

## 菜单识别

传统静态命令与动态 Shell 扩展使用不同的适配逻辑。一个动态扩展可能产生多个可见菜单项，需要在界面中说明操作影响范围。

HKEY_CLASSES_ROOT 是合并视图。扫描结果需要记录实际用户级或机器级来源，执行和恢复写回明确的原始位置。

菜单注册存在不等于一定在当前选择对象上可见。扫描结果应区分注册信息、推断状态和真实资源管理器验证结果。

对未知类型提供查看能力；只有适配并验证过的类型才提供修改操作。

## 变更与恢复

基本流程：确定实际来源 → 校验当前状态 → 持久保存恢复记录 → 修改 → 重新读取 → 保存执行结果。

恢复记录至少保存操作标识、时间、目标位置、注册表视图、值类型、原值、原先是否存在以及修改后的预期状态。涉及子键的操作应保存相应结构。

记录需要能区分准备、执行、成功及失败状态，以便应用异常退出后识别未完成操作。

恢复前对比当前状态与操作后的预期状态。如果目标被第三方软件更新或其他操作改动，应展示冲突，避免直接覆盖。

运行时设置、日志和恢复记录存储在应用数据目录，不放入源码仓库。

## 权限边界

普通权限完成扫描和允许的用户级操作。需要机器级写入时按需请求 Windows 权限提升。

前端传递菜单标识及用户意图，由 Rust 生成并校验变更计划。管理员辅助进程应独立校验目标及允许的操作，不提供任意注册表写入或任意命令执行接口。

Tauri capabilities 用于限制前端接口访问，不能替代 Windows 管理员权限控制。辅助进程涉及 HKCU 时应明确使用原始交互用户的身份和注册表位置。

## 验证重点

- 在隔离的测试注册表位置验证扫描、数据类型保存、变更和恢复逻辑。
- 在真实资源管理器中验证禁用后消失、恢复后重现。
- 验证文件、文件夹和空白处的作用范围。
- 验证自定义命令正确接收含空格、中文和特殊字符的路径。
- 验证拒绝提权、目标被外部修改、写入失败和未完成操作的处理。

## 当前实现状态

2026-10-14 界面确认后已实现 Tauri 2 + React + Rust 开发预览。桌面界面沿用确认的两栏布局、15px 菜单文字和按需详情侧栏。

Rust 已实现 64 位常见注册位置扫描、普通命令的 LegacyDisable 修改、持久恢复记录、冲突拒绝、按历史逆序恢复，以及当前用户的自定义菜单添加和撤销。

机器级修改由同一可执行文件的受限辅助入口执行：主进程通过 ShellExecuteEx 的 runas 动词请求提权，使用随机命名的本地管道通信，并校验辅助进程 PID。辅助入口仅允许在指定 HKLM 普通菜单键上修改 LegacyDisable，不接收任意执行命令、文件输出路径或任意注册表值名。主进程在提权前保存原始状态，并负责用户级日志。

恢复记录使用 JSON 文件，先写临时文件并同步，再替换正式记录。操作状态包括准备、完成、失败、恢复待检查及已恢复。时间戳采用 Unix 毫秒，同一进程内递增，以区分连续操作的先后。

当前限制和证据见 [验证记录](verification.md)，实际支持范围见 [使用说明](usage.md)。
